# 公開サイト（smartsprouts.jp）リニューアル 設計書

- 作成日：2026-10-30
- 状態：確定（2026-10-30、§11の未決事項にオーナー回答済み）。段階1に着手
- 元になる試作：`SmartSprouts/showcases/katsucoderenewal/`（静的HTML 29ページ。`scripts/build.mjs` が `src/data.mjs` と `src/*.html` から生成）
- 対象：未ログインで見る公開ページ（`PublicLayout` を使う画面）。管理画面・クライアント画面・Atlasは対象外

## 1. 目的

今の公開サイトは仮作りで、**ヘッダーメニューの13項目が404**になっている。試作 `katsucoderenewal` のデザイン（トップの3Dを含む）をReact（Inertia）に移し、あわせてリンク漏れを根本から直す。中身は管理画面「Webサイト管理」で編集できる形を保つ。

## 2. オーナー決定事項（2026-10-30）

1. **範囲**：まず「トップの3D＋共通ヘッダー・フッター＋メニューのリンク漏れ解消」から。下層ページは、管理画面「Webサイト管理」のデータと一致する形で作る
2. **ブランド表記**：試作の「Katsucode」を「SmartSprouts」に変える。ロゴはSの芽を共通で使う。フッターの電話・メール・所在地（奈良）は個人事業のままで、所有表記は「かつコード」
3. **記事・FAQ・会社情報**：リニューアル後も管理画面で編集できる形にする（コードに直接書かない）
4. **色**：試作の色（白と淡い緑）を採用する。全社ルール `company/rules.md` の基本色（黒・ゴールド・ライトグリーン）とは異なるが、承認済み

## 3. 現状の調査結果（開発環境、2026-10-30）

開発DBは2026-10-26時点のダンプ。本番の公開ページで見える範囲（メニューと404）は同じ状態だった。本番の管理画面の中身は見ていない。

### 3-1. リンク漏れの原因

ヘッダーメニューは管理画面「Webサイト管理」→「メニュー」のデータ（`menus.location = header`、`menu_items` 25件）。`MenuItemSeeder` で入った初期データのままで、どの項目も固定ページ（`page_id`）に紐付いていない。

| 404の項目 | 原因 |
|---|---|
| サービス配下6項目（`/service/web-development` など） | 実在するURLは `/services/{slug}`（複数形、サービス管理のslug）。メニューのURLが単数形で、slugも実データと違う |
| ソリューションと配下6業種（`/solution/...`） | 対応するページ・ルートが存在しない |

### 3-2. 公開ページと管理画面データの今の対応

| URL | 画面 | データ |
|---|---|---|
| `/` | `Public/Home` | 固定ページ `home` のセクション（hero / main / cta）、注目サービス、ほか |
| `/about` | `Public/About` | **コードに直書き**（管理画面で編集できない） |
| `/service`、`/services/{slug}` | `Public/Service`、`ServiceDetail` | サービス（21件公開）、サービスカテゴリ（10件） |
| `/blog`、`/blog/{slug}`、`/news`、`/news/{slug}` | `Public/Blog`、`BlogDetail` | 記事（60件。カテゴリ「ブログ」「お知らせ」） |
| `/faq` | `Public/Faq` | FAQ（32件、カテゴリ7件） |
| `/company` | `Public/Company` | 組織情報（`organizations`）、沿革（`organization_histories`） |
| `/contact`、`/estimate-simulator` | `Public/Contact`、`EstimateSimulator` | 機能あり（問い合わせ・見積） |
| `/privacy-policy`、`/terms` | 文書（`DocumentController`） | 文書管理 |
| `/lp`、`/lp-minimal`、`/lp-creative` | LP 3種 | コードに直書き |
| `/{slug}` | `Public/Page` | 固定ページ（`pages`＋`sections`）。最後に評価されるルート |

- 固定ページは8件（home・about・service・blog・company・faq・contact・privacy-policy）。ページ種別は7つ（トップ・固定・投稿一覧・LP・お問い合わせ・プライバシーポリシー・カスタム投稿一覧）
- 制作実績（`portfolios`）・お客様の声（`voices`）・サイト設定（`site_settings`）は、管理画面はあるが**0件**
- 共有プロップ：全公開ページに `headerMenu`（ヘッダーメニュー）と `organization`（組織情報：社名・代表者・電話・メール・営業時間・住所など）が渡っている。フッターの連絡先はこれを使える
- スタイル：`resources/css/app.css` で Tailwind（`@tailwind base` を含む）が全画面に適用されている。`PublicLayout` は公開ページ19画面で使われている

## 4. 全体方針

1. **URLは今のものを維持する**（検索エンジンの評価を落とさない）。新しく作るページだけ新URLにする
2. **画面はInertia＋React**。試作の静的HTMLは、`PublicLayout` と公開用コンポーネントに作り直す
3. **中身は管理画面のデータから出す**。コードに書くのは「デザイン上の固定の言葉（見出しの英字ラベルなど）」と「機能に結び付いたボタン（無料相談・料金の目安）」だけ
4. **スタイルは試作のCSSを移植する**。Tailwindで書き直さない（時間がかかり、見た目がずれる）
   - 置き場所：`resources/css/public/`（`renewal.css` と `concept.css` を元に、不要部分を削る）
   - 管理画面に影響させないため、公開レイアウトのいちばん外側の要素にクラス（例：`.ss-public`）を付け、その配下にだけ効くように書く
   - Tailwindの `base`（ブラウザ初期スタイルのリセット）が公開ページにも効いているので、移植後に見た目を試作と並べて確認する（§10のリスク1）
5. **3Dはトップだけで読み込む**
   - `three` をnpmの依存に追加する（バージョンは固定）。`gsap` は既存（^3.13.0）
   - 3Dのコンポーネントは動的インポートで別ファイルに分け、トップ以外では読み込まない（本番ビルドのメモリ不足 K22 の再発も避ける）
   - 試作の `engine.bundle.js`（842KB、three・gsapの同梱版）は使わない
   - `prefers-reduced-motion`（動きを減らす設定）と「動きを止める」ボタンに対応する。WebGLが使えない環境ではSVGのロゴを表示する（試作と同じ）
6. **ブランドの置き換え**
   - 「Katsucode」→「SmartSprouts」。試作に残る「HELLO, WE ARE KATSUCODE」「© 2026 Katsucode」なども置き換える
   - フッターの所有表記は「かつコード」。電話・メール・所在地・営業時間は `organization` から出す（コードに直書きしない）
   - 試作の「試作」表示と、全ページの `noindex,nofollow` は付けない
7. **作業はブランチで行い、段階ごとに本番へ反映する**（§8）

1. 開発環境の管理画面で、新しいヘッダーメニュー・フッターメニューを作って確認する
2. 確認できた内容を「本番で入れる項目の一覧」にして、オーナーが本番の管理画面で同じように入力する
3. 反映後、公開ページを辿ってリンク切れが0件であることを確認する（`~/dev/spra-check`）

## 10. リスク

1. **Tailwindの初期スタイルとの衝突**：Tailwindの `base` が公開ページにも効いているため、移植したCSSの見出し・リスト・ボタンなどが試作と違って見える可能性がある。移植後に試作と並べて確認し、必要なら公開レイアウト配下で上書きする
2. **ビルドのメモリと容量**：`three` は大きい。トップ専用の別ファイルにし、本番ビルドのメモリ（K22）を確認する
3. **開発DBと本番の差**：開発DBは10/26時点。本番の管理画面のデータ（メニュー・固定ページのセクション）が違う可能性がある。段階1の反映前に、本番の該当データをオーナーと確認する
4. **文章の量**：試作の文章はかつコード向けで、そのままは使えない。書き直しの確認に時間がかかる
5. **画像**：試作の実績画像（クライアントのサイト）は、smartsprouts.jpでの掲載可否を確認してから使う

### 13-2. 設計から変えたこと

| 項目 | 設計 | 実装 | 理由 |
|---|---|---|---|
| お問い合わせ・概算見積もり | 「既存の機能のまま、見た目だけ変える」 | **見送り**。`PublicLayout`の非renewedモード（段階1で用意した、ヘッダー・フッターだけ新しくする経路）のまま | フォーム・見積ウィザードのロジックが大きく（Contact 374行、EstimateSimulator 1003行）、作り直しのリスクと工数が大きいため。すでに新しいヘッダー・フッターは適用されている |
| 事業者情報の住所 | 組織情報をそのまま表示 | **都道府県・市区町村までに絞った**。番地（`district`/`address_other`）・郵便番号は表示しない | 個人事業主の自宅兼事務所の番地が公開され得ることに気づいたため（試作も同じ理由で「詳細はご契約の際にお伝えします」としていた）。あわせて、公開サイト全ページで共有している`organization`プロップ自体から番地・郵便番号を除外した（`HandleInertiaRequests`）。これらの項目は元々、全ページの初回表示データに含まれていたが、画面に出していなかっただけだった。管理画面の組織編集画面は、各コントローラーが別途フルの組織情報を渡すため影響しない |
| 私たちについて・事業者情報 | 代表紹介・採用情報への導線を含む | 外した | リンク先（`/greeting`、`/recruit`）が段階3未着手のため |
| サービス詳細の「できることの一覧」 | 試作の4項目チェックリスト（手書き） | 出さない。`description`/`details`（既存データ）のみ表示 | 21件分の個別原稿が無く、作文で埋めると事実と異なる内容になるため |
| 料金プランの並び | 試作に無い（固定ページの料金表は別物） | `.price-entry`を流用した新規の`.plan-grid`で表示 | 試作に複数プランを並べるデザインが無かったため |
